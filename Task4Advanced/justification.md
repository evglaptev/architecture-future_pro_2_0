## Почему событийная архитектура

| Критерий | Шина Camel + DWH | Event-driven подход |
| --- | --- | --- |
| Time-to-market | Каждая интеграция требует синхронных маршрутов, правок в SQL Server и PowerBuilder | Домен публикует события один раз, downstream подключаются самостоятельно; новые витрины собираются из потоков |
| Масштабируемость | Монолитная БД и ESB становятся bottleneck при росте объёма | Kafka/Flink масштабируются горизонтально, данные разделены по доменным topics |
| Независимость доменов | DWH содержит бизнес-логику, сложно выделить ответственность | Bounded contexts владеют своими агрегатами и событиями; Data Mesh обеспечивает контрактный слой |
| Near-real-time | DWH работает пакетами, отчёты строятся часами | Потоки доставляют события за секунды, self-service BI читает свежие данные |
| Надёжность | Camel-маршруты трудно тестировать, откаты выполняются вручную | События версиируются, хранятся в журнале, можно переигрывать и восстанавливать состояние |
| Подключение партнёров | Требует индивидуальных адаптеров на Camel | Партнёры получают AsyncAPI и могут публиковать/слушать события с mTLS |

### Управленческие выгоды

- Доменные команды получают ответственность за свои события и дата-продукты, что совпадает с внедрением Data Mesh.
- Self-service портал работает поверх согласованных контрактов, больше не зависит от PowerBuilder.
- Регуляторные требования выполняются через централизованные политики доступа (Keycloak + OPA) и аудит событий.

### Технические выгоды

- Потоковые события служат единым источником правды для lakehouse, AI и финтех сервисов.
- Легаси DWH используется только как «bridge» до полного перевода домена.
- Повышается обсервабилити: каждое событие логируется, есть DLQ и каталог схем.
